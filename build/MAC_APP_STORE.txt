Mac App Store preparation (not a release-ready configuration)

The default dist:mac command remains the direct-download, ad-hoc signed build.
It must not be used to create an App Store submission.

mac-app-store.template.cjs is an isolated configuration template. It requires:
- SCREENPLAY_MAS_MODE: development or distribution (no implicit default)
- SCREENPLAY_MAS_TEAM_ID: the real Apple Developer Team ID
- SCREENPLAY_MAS_SIGNING_IDENTITY: the actual development or distribution
  certificate name; a certificate CN suffix is not necessarily the Team ID
- SCREENPLAY_MAS_PROFILE: an absolute path on the Mac to the matching profile
- SCREENPLAY_MAS_BUILD_NUMBER: an explicit, unused, Apple-compatible build number

Keep signing keys, exported certificates and provisioning profiles outside the
repository. Use the Mac keychain for signing identities. Do not paste passwords
or private keys into chat, tests, build files or diagnostics.

The template disables automated publishing. It does not upload or submit an app.
Existing direct-download outputs and release scripts are not changed.

Read-only native environment check:
node scripts/mac-app-store-environment.cjs --team YOURTEAMID
This reports tool versions and matching signing-identity availability only.
It does not export keys, create certificates, alter the keychain, verify a
provisioning profile, or establish that a submission is ready.

An isolated, credential-free cloud macOS toolchain check is also available:
.github/workflows/mac-app-store-preflight.yml
It is deployed only on branch mac-app-store-preflight-20261024, not main.
Both Intel and Apple Silicon jobs passed with Xcode 26.6 and macOS SDK 26.5.
https://github.com/uberadamfor4-ui/screenplay-studio/actions/runs/40063893885
No account password or signing secret was needed for that toolchain check.
This does not establish that signing-secret administration is available through
the existing connection, nor replace app sandbox, signature or installation QA.
The modern build-host choice does not change the app minimum supported macOS.

Implemented in the candidate, still pending real MAS sandbox acceptance:
- Persistent security-scoped bookmarks with bounded, atomic local storage.
- Balanced access lifetimes, stale-folder reauthorization and canceled-save safety.
- Folder authorization before atomic replacement; save panels do not create empty
  placeholder files before overwrite protection has completed.
- The font/style acceptance uses the same offscreen PDF renderer as production,
  rather than an independent hidden print window with different settings.
These paths have synthetic regression coverage; this is not native sandbox proof.

Submission blockers still require implementation or native acceptance:
- Explicit, reversible migration from non-sandboxed user data.
- Fonts, native PDF canvas, imports, attachments and PNG exports under sandbox.
- Real Mac screenshots, privacy policy, privacy disclosures and store metadata.
- Profile / Team ID / App ID / signing verification and App Store Connect checks.
- Native testing of all architectures advertised in the Universal package.

The entitlements alone DO NOT implement file access or prove sandbox readiness.
Do not submit a build created from this template until those checks are complete.
Keep matching private signing keys on the owner's Mac where possible. Cloud tool
availability does not establish permission to export those keys or sign an app.
